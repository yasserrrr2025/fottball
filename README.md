# نظام تسجيل واعتماد لاعبي فريق كرة القدم

مشروع Next.js عربي RTL مرتبط بـ Supabase لإدارة تسجيل 20 لاعبًا لفئة U13 بنين في مدرسة عماد الدين زنكي المتوسطة.

## الوظائف

- تحقق الطالب برقم الهوية وإظهار اسمه المسجل فقط.
- نموذج بنكي شرطي: حساب الطالب أو حساب ولي الأمر.
- اسم ولي الأمر ورقم جواله عند عدم وجود حساب للطالب.
- رفع صورة أو PDF لشهادة الآيبان إلى Bucket خاص.
- OCR محلي عبر Tesseract للصور ومحاولة مقارنة الآيبان المدخل بالمرفق.
- لوحة إدارة عبر `/admin`.
- إضافة الطلاب يدويًا أو استيراد Excel.
- مراجعة الطلبات، فتح المرفق برابط مؤقت، اعتماد، إعادة للتصحيح، رفض، وإعادة فتح الطلب المعتمد.
- سجل تدقيق للإجراءات الإدارية.

## 1) إعداد Supabase

1. أنشئ مشروعًا في Supabase.
2. افتح **SQL Editor**.
3. نفّذ الملف `sql/supabase_setup.sql` كاملًا.
4. من **Authentication > Users** أنشئ مستخدم الإدارة بالبريد وكلمة المرور.
5. نفّذ السطر التالي بعد تغيير البريد والاسم:

```sql
insert into public.admin_users (user_id, full_name)
select id, 'مدير النظام' from auth.users where email = 'admin@example.com'
on conflict (user_id) do update set is_active = true;
```

## 2) متغيرات البيئة

انسخ `.env.example` إلى `.env.local`:

```env
NEXT_PUBLIC_SUPABASE_URL=https://YOUR_PROJECT.supabase.co
NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY=sb_publishable_xxx
SUPABASE_SERVICE_ROLE_KEY=sb_secret_xxx
NEXT_PUBLIC_SITE_NAME=تسجيل لاعبي فريق كرة القدم
```

لا تضع `SUPABASE_SERVICE_ROLE_KEY` في متغير يبدأ بـ `NEXT_PUBLIC_`، ولا تشاركه مع أي شخص.

## 3) التشغيل

```bash
npm install
npm run dev
```

- بوابة الطالب: `http://localhost:3000`
- لوحة الإدارة: `http://localhost:3000/admin`

## ملف Excel

الصف الأول يجب أن يحتوي على عمود للاسم وعمود للهوية. أمثلة أسماء الأعمدة المدعومة:

- `اسم الطالب` أو `الاسم`
- `رقم الهوية` أو `رقم الإقامة`

يعرض الاستيراد عدد الصفوف المستوردة وغير الصحيحة. يمنع تكرار رقم الهوية.

## التحقق من الآيبان في الصورة

- يعمل OCR تلقائيًا للصور JPG وPNG وWEBP.
- ملفات PDF تُحفظ وتظهر للمراجعة اليدوية، وحالتها `unsupported` حاليًا.
- نتيجة OCR مساعدة، ولا تعتمد الطلب تلقائيًا.
- حالات التحقق: مطابق، غير مطابق، لم يعثر عليه، نوع غير مدعوم، أو فشل القراءة.

## ملاحظات الأمان

- قائمة الطلاب لا ترسل إلى المتصفح العام.
- التحقق العام يتم عبر Route Handler في الخادم.
- الملفات في Bucket خاص وتفتح للإدارة بروابط موقعة مدتها خمس دقائق.
- RLS مفعل على الجداول.
- مفتاح Service Role يستخدم في الخادم فقط.
- بعد الاعتماد لا يستطيع الطالب تعديل الطلب إلا إذا أعادت الإدارة فتحه.

## المزايا التشغيلية المضافة

- لوحة مؤشرات تنفيذية ونسبة اكتمال اعتماد الفريق من أصل 20 لاعبًا.
- مركز مراجعة موحد يعرض الآيبان المدخل والمستخرج ونتيجة مطابقة الصورة والبنك وسجل الإجراءات.
- اعتماد والانتقال مباشرة إلى الطلب التالي.
- جدول قابل للإدارة لأكواد البنوك الرسمية `bank_codes` للتحقق من توافق البنك المختار مع رمز البنك في الآيبان.
- تجهيز رسائل واتساب للحالات: الاستلام، الإعادة للتصحيح، الاعتماد، والرفض.
- رابط تصحيح آمن صالح لمدة 72 ساعة.
- تصدير Excel مطابق لترتيب أعمدة ملف الفريق الرسمي.
- سجل تدقيق بالقيم السابقة والجديدة لكل إجراء.
- إقرار إلزامي بصحة البيانات واستخدامها مع حفظ وقت الموافقة وإصدار النص وبصمة مشفرة لعنوان الاتصال.
- بطاقة رقمية احتفالية بعد إرسال البيانات.

### إعداد أكواد البنوك

لم تُدرج أكواد بنوك تخمينية. أدخل الأكواد الرسمية المعتمدة لديك في جدول `bank_codes`:

```sql
insert into public.bank_codes (code, bank_name)
values ('00', 'اسم البنك')
on conflict (code) do update set bank_name = excluded.bank_name;
```

### رابط الموقع

أضف إلى `.env.local` حتى تنشأ روابط التصحيح بشكل صحيح:

```env
NEXT_PUBLIC_SITE_URL=https://your-domain.example
```


## تحديث قائمة البنوك

- قائمة البنوك ثابتة داخل `lib/banks.ts`.
- حقل البنك قائمة بحث عربية؛ يكتب الطالب جزءًا من الاسم ثم يختار نتيجة معتمدة.
- لا تعرض شعارات البنوك.
- لا يستنتج النظام البنك من رقم الآيبان ولا يقارن رمز البنك بالاختيار.
- يستمر التحقق من صيغة الآيبان ومطابقته مع الرقم المستخرج من المرفق فقط.
